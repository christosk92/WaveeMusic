## Locked decisions (orchestrator rulings — do not re-litigate)

1. **No phased legacy compatibility.** Nothing is shipped to anyone; the only DB that must survive is the developer's own `%LOCALAPPDATA%\Wavee\library.db` at schema v4. One migration (v5) goes straight to the end-state schema. Legacy `entities`, `localized_entities`, and the dead indexes are DROPPED in v5. No rollback-window ceremony (critique #8 is moot by fiat).
2. **Identity tables are sacred.** `collection_items`, `collection_rev`, `playlists` (incl. `base_rev`), `playlist_items`, `rootlist`, `outbox`, `dead_letter`, `video_override`, `meta` are never dropped, rewritten, or lossy-migrated. Everything else is re-fetchable cache by definition.
3. **Migration v5 content:** create end-state tables (`entity`, `entity_refs`, `artist_overview`, `recent_surfaces`); migrate ONLY pin-reachable rows from the union of `entities`+`localized_entities` (localized wins conflicts); thin scalar columns extracted in C# via the existing STJ `EntityJson` models; payloads stored fmt=1 (zstd level 3); non-pin-reachable rows are simply not migrated (that IS the one-time GC); drop legacy tables + `ix_localized_entities_locale`, `ix_localized_entities_updated`, `ix_localized_extension_locale` (keep `ix_localized_extension_expiry`); set `vacuum_pending` meta flag; full VACUUM + `auto_vacuum=INCREMENTAL` runs in background AFTER first paint, gated on that flag.
4. **Encoding:** System.Text.Json source-gen (existing `EntityJson` context) + ZstdSharp level 3, 1-byte fmt prefix on every payload (0=raw JSON, 1=zstd). **NO `WhenWritingDefault`** (critique #5: corrupts `Playlist.IsPublic`; zstd already gives the size win). No trained dictionary in this pass (fmt=2 reserved).
5. **No covering list index** (`ix_entity_list` from design §A.2 is dropped per critique #9d — payload-last rows fit a page; PK point reads suffice). Keep `ix_entity_gc(kind, last_access)` only.
6. **Two SQLite connections** (critique #2): the existing writer connection keeps `_connLock`; add a dedicated read-only connection (`SqliteOpenMode.ReadOnly`, WAL) with its own lock for all point reads (`GetEntity`, `ColdFallback`, rootlist/membership loads). Background warm/GC/vacuum ride the writer; UI-facing reads never queue behind them.
7. **Warm set is bounded; residency is NOT the search substrate** (critique #3). `WarmAsync` loads: saved-set entities + recent_surfaces entities + rootlist playlist headers (a few thousand rows), under `BeginBulk`, one bulk signal. The 12k/8k backstop is untouched. Offline library search (`QueryTracks` / `LibrarySearchIndex`) is rebased onto SQL against `entity` thin columns joined to `collection_items`/`playlist_items` — correct at any scale, no full residency required. `InitialHydrate` gates on `WarmComplete`.
8. **`video_assoc` stays eagerly loaded** in the deferred ctor (critique #4 — hot-only reader + video-edge fragility; it's ~2 MB).
9. **Pin gate + pin-transition flush** (critique #1): the six `Upsert*` chokepoints gate cold persistence on pin-reachability; `SetSaved`/`SetMembership`/video-override-attach flush the hot entity to cold when cold lacks it; the no-op elision key = (payload hash, cold-presence bit).
10. **Pin set** = collection_items ∪ playlist_items ∪ playlists ∪ rootlist ∪ outbox.entity_key ∪ video_override ∪ recent_surfaces ∪ entity_refs closure (pinned track → its album/artists), plus the in-memory `BuildPinSet` snapshot **taken on the UI thread and marshaled** to the GC thread (critique #10). Derived at GC time, never a stored boolean. Unpin ≠ purge.
11. **Membership GC** (critique #6): playlists NOT in rootlist AND NOT in recent_surfaces AND last adopted > 14 d ago → their `playlist_items` rows are deleted at GC (metadata rows then age out via TTL). Own-library playlists are always in rootlist, so user data is untouched.
12. **Discography** (critique #7): `DiscographyPrefetcher` cold-persists ONLY when the artist is in the saved set (bounded ~10–20 cards/saved artist); otherwise hot-only. `LiveContextResolver` autoplay/radio hydration: hot-only. Browsed-album embedded tracks: hot-only unless pin-reachable.
13. **TTL/LRU:** unpinned entity 30 d since last_access; `artist_overview` 7 d since fetched_at; extensions `expires_at` + 7 d grace; budget default 64 MiB (`cache_budget_bytes` meta), watermark 0.9×, DELETE batches ≤ 1000 rows, 15-min new-row grace. Last-access at day granularity, batched flush on the writer thread (60 s / idle). GC at warm+30 s and every 6 h. `PRAGMA incremental_vacuum(200)` slices on idle; no routine full VACUUM.
14. **Extension cache:** `LoadAllExtensions` takes `LIMIT` matched to live `maxEntries` = **2048** (not 4096); expired sweep at open uses the +7 d grace (critique #12).
15. **`IN (...)` chunking:** any URI list query chunks at ≤ 900 parameters or uses a temp table (critique #14).
16. **Escape hatches:** `cache_budget_bytes` setting, "Clear metadata cache" (unpinned cache tier only + artist_overview + extensions, never identity, then incremental_vacuum), startup marks (`boot.sqlite_open_ms`, `boot.identity_load_ms`, `boot.first_paint_ms`, `boot.warm_ms`, `boot.warm_rows`) + per-GC report to wavee.log. **NO env kill switches** (user ruling 2026-07-27): GC + the write gate are unconditionally the default behavior — no `FG_NO_ENTITY_GC`, no persist-everything fallback flag.
17. **Artist split:** persisted Artist core ≈ 1 KB (Id/Uri/Name/Image/HeaderImage/Palette/Verified/MonthlyListeners/Followers); TopAlbums/AppearsOn/PopularReleases/LatestRelease/Pinned/TopTracks/Bio/Extras → `artist_overview` as (uri, kind, name, year, cover_url) refs + bio/extras/stats, AppearsOn capped at 100 at projection. `StoreEntityMerge.Artist` SWR/clobber gates preserved: core gates stay on core, TopTracks-presence stats gate moves to the overview merge. Hot tier keeps full records; `ArtistDiscography.Assemble` re-fattens from standalone rows + overview.
18. **Tests:** Wavee.Tests compiles app sources via explicit `<Compile Include>` — every new class needs an entry. New coverage required: v4→v5 migration fixture, fmt round-trip, pin gate, pin-transition flush, elision, GC (TTL/budget/pin-exempt/membership-GC), WarmAsync readiness, artist split + assemble, SQL-backed offline search.

## Addenda from pre-wave recon (binding on Waves B–D; see scratchpad recon-wave-d-surfaces.md)

A1. **`LiveContextResolver` needs no edit.** Its only persistence is indirect via `MetadataService.SyncAllAsync` → `ExtendedMetadataSource` upserts → the six `CachedStore.Upsert*` chokepoints. The Wave B pin gate makes its transient hydration hot-only automatically. Do not add a gate inside the resolver.
A2. **`DiscographyPrefetcher` is already saved-scoped** (starts from `SavedUris("artists")`, DiscographyPrefetcher.cs:22). To satisfy critique #7 (offline discography for saved artists), the pin-reachability rule is extended: an Album is pin-reachable if any of its `ArtistRefs` is in the saved-artists set; an Artist is pin-reachable if in the saved-artists set. No prefetcher edits needed beyond what the gate provides.
A3. **`entity_refs` is written for albums and artists too, not just tracks** (Wave B): track→album + track→artists (Wave A), album→artists, artist→albums (from the overview's discography/TopAlbums refs). Needed because the offline library search cascade (artist matched → all its albums → all their tracks) becomes a refs join after the artist thin split — post-restart, hot artists are thin cores and `artist.TopAlbums` walks no longer work as the search corpus.
A4. **SQL-backed library search must preserve UI contracts** (Wave D): (a) `MatchStart`/`MatchLen` highlight offsets (use ordinal IndexOf on the returned rows in C#, never rely on SQL `instr` for offsets); (b) match semantics stay `OrdinalIgnoreCase` — do SQL coarse-filtering (`LIKE` with NOCASE) as a candidate pre-pass ONLY if it is provably a superset, otherwise filter in C# over thin rows; (c) the inclusion cascade + `MatchReason` attribution + ranking (own-name first, year desc, name tiebreak, ArtistCap 200) reproduced exactly; (d) `AggregateCatalog` treats empty as fall-through (AggregateCatalog.cs:129-136) — an offline-with-no-matches result must remain `Empty` (existing behavior) but be aware of the semantic; (e) result groups need Cover/Image — thin columns carry image_url, map it.
A5. **`recent_surfaces` hook** = `WaveeShell.Go` (WaveeShell.cs:711-723, UI thread) using the existing `ParseDetail`/`UriOf` classifiers (DetailPage.cs:26-33, ArtistPage.cs:35-36, ContentHost.cs:96-100); writes are snapshot-then-`Task.Run` fire-and-forget (mirror HistoryStore.SaveToDisk, HistoryPage.cs:100-124). A6. **Write-behind lag**: entity writes flush batched (SqliteColdStore write-behind); SQL-backed search reads may miss rows queued in the lane — acceptable (documented pre-existing semantics, ColdStore.cs:36-39), do not add flush-on-search.

## As landed (Wave F addendum — deviations, resolutions, known residuals)

Every locked decision above held. What differs from the letter of the plan, and what Wave F changed:

**Deviations from the plan text (all deliberate, none re-litigating a locked decision):**

1. **Schema went to v6, not v5.** v5 is the cache-tier end state as specified; v6 is one purely additive column on an identity table — `playlists.adopted_at`, the clock locked decision 11's membership GC dates its victims by. Backfilled to "now" so no existing playlist is instantly 14 days stale.
2. **Membership GC also deletes the `playlists` HEADER row**, not just `playlist_items` (locked decision 11 names only the items). It has to: `SELECT uri FROM playlists` is a §A.3 P0 pin leg, so leaving the header behind would keep the playlist pinned forever and the GC would reclaim nothing. Cost is the foreign playlist's `base_rev` (its next open is a full fetch instead of a delta). Guarded five ways — not in rootlist ∧ not a recent surface ∧ no outbox intent ∧ not a collection item ∧ adopted > 14 d ago — and own-library playlists are always in the rootlist.
3. **`RecentSurfaceRoute` does NOT reuse the UI route parsers** (`DetailPage.ParseDetail` / `ArtistPage.UriOf` / `ContentHost.IsDetail`), contrary to Addendum A5's "using the existing classifiers". Pinning is a narrower question than page routing: `liked` is a set with no entity row and `local` resolves to the synthetic `wavee:local:all`, and recording either would burn one of the 50 LRU slots on a row that can never be read back. It lives in `Backend/` so it is unit-testable without the shell.
4. **`PersistAlbum` caps the persisted `Hydration` at `Tracks`.** A `Full` cold row with the facet lists stripped would suppress the very `getAlbum` refetch that rebuilds them (`SpotifyAlbumEnrichmentService` reads that flag). Safe because `StoreEntityMerge.Album` keeps the HIGHER of the two levels.
5. **No SQL pre-filter in the offline search** (Addendum A4(b) allowed a `LIKE`/`NOCASE` candidate pre-pass "only if provably a superset"). It is not: SQLite `NOCASE` folds ASCII only, so it is strictly NARROWER than the `OrdinalIgnoreCase` the UI matches with and would silently drop Ω/ω, İ, ı. SQL answers "what is in scope"; C# answers "what matches, and where".
6. **The v5 `entity` table keeps no album index.** `ix_entity_list` was dropped per critique #9d as planned, but note the consequence for §E below.

**Wave F — confirmed findings, fixed (each with a test in `Wavee.Tests/PersistenceWaveFTests.cs`):**

- **F1 · The GC re-armed critique #1.** `CachedStore._coldRows` doubles as the "this uri has a row on disk" bit and the payload-hash elision key, and nothing told it when the collector DELETED a row. The stale bit then made BOTH guards fail closed: `EnqueueFlush` short-circuits ("already on disk") so a later pin transition never re-persists, and `PersistEntity` elides ("bytes unchanged") so the ordinary re-write does not either. A like → unlike → 30-day age-out → re-like sequence stranded the track off disk permanently and it vanished from Liked Songs after the next restart. Fixed: the sweeps report their victims (`GcSweepUnpinnedEntities`/`GcEnforceBudget` take an `evicted` sink, bounded at 20 000 uris then degrading to "clear the map"), and `EntityCacheGc` feeds them to the new `CachedStore.OnEntitiesEvicted` / `OnOverviewsEvicted` in a `finally`, so even a failed or cancelled pass resyncs.
- **F2 · `temp.gc_pin` collision.** `ClearMetadataCache` and a GC pass both built their pin table under the same name on the same writer connection, where temp tables are connection-scoped. A settings-triggered clear interleaved between two GC batches dropped and rebuilt the pass's pin table — aborting the pass, and worse, swapping in a table WITHOUT its UI-thread exempt snapshot. The clear now uses `temp.clear_pin` / `temp.clear_kids`.
- **F3 · Overlapping GC passes.** `RunOnceAsync`/`RunPass` are public and would clobber each other's temp tables; `RunPass` now serializes on a pass gate.
- **F4 · `SqliteColdStore.Flush()` waited unbounded** on its queue marker. Bounded to 30 s so a pathological backlog can never wedge shutdown.

**K1 — `cache_budget_bytes` below the extension+pinned floor: CONFIRMED, fixed.** `cache_bytes` counts the extension cache (18.5 MB on the developer's real db) and every pinned entity row, but `GcEnforceBudget` may only delete UNPINNED entity rows. Measuring an unreachable ceiling against the gross counter did not merely fail to converge — it emptied the ENTIRE unpinned tier and was still "over budget". The trigger is now `GcEvictableBytes()` (`SUM(size)` over rows `temp.gc_pin` does not protect), seeded once per sweep and decremented by each batch's exact freed bytes, so the loop converges precisely and never sacrifices rows to an impossible goal. `EntityCacheStats` gained `EntityBytes`/`EvictableBytes` and the Settings → Storage readout now shows `evictable X of Y budget` — the number the budget actually governs. (The 32 MiB `Services.MinMetadataCacheBudgetBytes` floor stays; it is now a floor on evictable metadata, which is the honest reading.)

**K2 — migration keeps fat artist cores: CONFIRMED benign, fixed anyway.** Reading a fat migrated core is *correct* either way (`Replay`/`ColdFallbackArtist` only re-fatten when an overview row exists), so this was purely a size issue — but the answer to "does the heal fire for a pinned artist that is warm-loaded and never re-fetched?" was **no**: `Replay` upserts the fat record into the hot tier directly, bypassing `CachedStore.UpsertArtist`, so nothing re-persisted it and `artist_overview` stayed empty for that artist until an online ArtistV4 SWR pass. The warm replay now splits it once, offline, with no network fetch: it already holds the fat record and already knows the row is pin-reachable (it came out of the pin head-set). A row that is already thin projects to an empty document and writes nothing. On the developer's db this retires the last ~350 fat cores (41 % of the entity payload bytes) on the next launch.

**K3 — migration stamps `last_access = now` on every row: ACCEPTED, no fix.** It restarts the 30-day TTL clock for the whole tier, but the tier it restarts it for is *by construction* the pin-reachable set: the migration only copied pin-reachable rows, and the TTL sweep only ever deletes UNPINNED rows. The restarted clock therefore only matters for rows that later become unpinned (unlike/unfollow/membership GC) — for which "30 days from the generation change" is the correct, conservative reading anyway. Same for the `adopted_at = now` backfill (Wave E §5.5): the first membership GC purges nothing, and the 169 non-rootlist playlists become eligible 14 days after the migration.

**Known residuals (documented, not fixed):**

- **Pin-snapshot staleness across a batched GC** (critique #11, still open by design). The pin table is materialized once at `GcBeginPass`; a playlist adopted mid-pass pins entity rows the snapshot saw as unpinned, and a later batch can delete them, leaving membership rows referencing missing entities until an online heal. The 15-minute `updated_at` grace covers rows written during the pass, so the exposure is the seconds-wide window over rows that were already old. Closing it properly means re-deriving the pin table per batch, which is exactly the O(n) cost the batching exists to avoid.
- **`video_assoc` is asymmetric.** `GcDeleteLoop` deletes the association of an evicted entity (a dangling row is unreadable) while `ClearMetadataCache` deliberately does not touch the table at all (locked decision 8 — the video-edge map is eagerly loaded and fragile). Rows whose entity was never in `entity` are never reclaimed and are not counted in `cache_bytes`; bounded in practice (7 118 rows on the real db) but unbounded in principle.
- **Per-keystroke candidate-query cost.** `entity` has no index on `album_uri`, so the `SavedArtists`/`SavedAlbums` scopes' "those albums' tracks" leg is a scan of the track rows per keystroke (~14 k rows / a few ms today, ~100 ms at a 155 k-row library). Adding `ix_entity_album(album_uri)` is a v7 schema change and was judged out of scope for this wave; revisit if a large library feels sticky in the library search box.
- **`PayloadCodec`'s `[ThreadStatic]` zstd contexts** are per-thread and never disposed. `Decode` runs on whichever thread reads, including thread-pool threads under `Task.Run`, so the worst case is one decompression context per live pool thread. Bounded and small in practice; noted because it is invisible in the code.
- **No app-level `CachedStore.Flush()` on shutdown** (pre-existing, unchanged). WAL + the committed write-behind batches make this safe; only the last un-drained batch is lost, and every entity in it is re-fetchable cache.
- **Stale prose in superseded planning docs.** `docs/plans/wavee/library-sync-fix-proposal.md:143,176` and `docs/plans/wavee/library-sync-implementation-plan.md:19` still describe "`CachedStore` bulk-loads SQLite at startup". They are the historical record of a different, already-landed campaign and were left as written; the live contract is this file plus the class comment on `CachedStore`. `Backend/Persistence/ColdStore.cs`'s header carried the same stale claim in *code* and was corrected in Wave F. `CLAUDE.md`, `docs/guide/`, and the `wavee` skill never asserted full residency.
