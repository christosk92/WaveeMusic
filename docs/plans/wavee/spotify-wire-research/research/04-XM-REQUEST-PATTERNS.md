**requestPatterns:**
  1. CORPUS: 13 captures scanned (omg, all, VIDEO, playback_remote, content-filters, concerts, concerts_v2, artist_more, someMoreMaybe, playlists, pre-release, final .saz + the pre-extracted spotify.saz raw dir) = 9,170 HTTP sessions, of which 2,718 are POST /extended-metadata/v0/extended-metadata. Those carry 306,449 EntityRequests and 969,064 ExtensionQuery entries. Responses returned exactly 969,064 EntityExtensionData items — the server emits EXACTLY ONE response item per query, always, never fewer, never more, and in request order. Wavee can therefore zip request/response positionally.
  2. BATCH CEILING — the 300 limit is CLIENT-VERSION-SCOPED, not server-scoped. Spotify-App-Version 129400583 (2,471 POSTs): max entities/POST = 300, hard, never exceeded; the size histogram tops out at 295,296,297,298,299,300 with 792 POSTs at exactly 300. Version 129300667 (247 POSTs, only present in all.saz): max = 1,425 entities in ONE POST (1 sample, all spotify:track / TRACK_V4 only), plus 13 POSTs at exactly 500, 2 at 457, 1 at 496. So the true observed max is 1425 entities, and the 300 ceiling is a client-side paging constant introduced in 129400583 (the server accepted 1425 and answered all of them with 200s).
  3. QUERIES per POST (entities x kinds) max = 3,003; p99 = 1,708; median = 27. The largest well-formed POST is 300 entities x ~6 kinds = 1,800 queries; the 3,003 case is a 300-entity POST where some entities carry up to 11 kinds. Compressed request bodies are gzip (Content-Encoding: gzip on the REQUEST), responses are zstd.
  4. PER-KIND max entities in a single POST: 300 for essentially every batchable kind (TRACK_V4 the exception at 1425 on the old client; ALBUM_V4 500 on the old client). Kinds with their own lower ceilings observed: 239 ContentCapabilityTrait max 100, CANVAS_V1 max 85, AUDIO_FILES max 50, LIST_TUNER_AUDIO_ANALYSIS max 50, 237 ThreeBandWaveforms max 50, 225 MixState max 30, ROOTLISTABILITY_TRAIT max 30, PODCAST_SUBSCRIPTIONS max 41, 220 EntityTypeTrait max 23, ON_PLATFORM_REPUTATION_TRAIT max 25, PUBLISHING_METADATA_TRAIT max 10. Single-entity-only kinds (max 1 per POST, always): SMART_SHUFFLE, AUTO_LENS, USER_PROFILE, 246 CurationExperienceTrait, WATCH_FEED_ENTITY_EXPLORER, PRERELEASE, TRANSITION_MAPS, PODCAST_RATING, RECOMMENDED_PLAYLISTS, AUTOMIX_MODE.
  5. SURFACE BUNDLE — 'track row hydration' (the dominant one, 73,003 entities): per-track query set {178 IDENTITY_TRAIT, 179 VISUAL_IDENTITY_TRAIT, 182 CONSUMPTION_EXPERIENCE_TRAIT, 212 PLAYBACK_TRAIT, 249 ContentExperienceTrait} — 5 kinds, no TRACK_V4.   12. ETAG USAGE: only 29,657 of 969,064 queries (3.06%) carry an etag. But etags WORK: 25,939 of those 29,657 (87.5%) came back 304, and NOT ONE 304 was ever returned for an etag-less query (0 of 939,407). So the 304 is purely etag-driven. Overall 304 rate across all queries = 2.68%; overall 404 rate = 2.89% (27,979). Etag-bearing queries never 404 and never 5xx.
  13. ETAG SHAPE: opaque bytes, length is per-kind and stable — 16 bytes for TRACK_V4 / 222 AudioAttributes / 85 ORIGINAL_VIDEO / 9 ALBUM_V4 / 225 MixState (ASCII-hex-looking, e.g. TRACK_V4 etag b'3946433744373633'), 8 bytes for 182 / 179 / 99 / 239 / 16 CANVAS_V1, 54 bytes for 12 EPISODE_V4, 60 bytes for 164 GATED_ENTITY_RELATIONS. Wavee should store the etag as an opaque blob per (uri,kind), never parse it.
  14. ETAG ADOPTION IS PER-KIND, NOT UNIFORM. Kinds where the client almost always sends an etag: 6 TRACK_DESCRIPTOR 95.9%, 183 PUBLISHING_METADATA_TRAIT 87.1%, 170 AUTO_LENS 85.3%, 11 SHOW_V4 72.2%, 225 MixState 67.3%, 54 HTML_DESCRIPTION 66.9%, 21 EPISODE_TRANSCRIPTS 62.0%, 12 EPISODE_V4 52.7%, 239 48.2%, 164 45.4%, 16 CANVAS_V1 39.7%. Kinds where it essentially never does: 212 PLAYBACK_TRAIT 0.02%, 249 0.06%, 178 IDENTITY_TRAIT 0.17%, 179 0.8%, 182 2.4%, 10 TRACK_V4 5.9%, and 98/30/58/31/4/22 at literally 0%.
  15. ETAG SOURCE IS A PERSISTENT DISK CACHE, NOT SESSION MEMORY. Of first-in-capture occurrences of a (uri,kind) pair, 22,421 already carried an etag on the very first request of the session. Conversely only 3.1% (1,854 of 60,555) of SECOND-and-later in-session occurrences carried one. The client is not learning etags from the responses it just received within the session; it is replaying etags from a durable store. Wavee must persist etags across restarts to get any benefit.
  16. RE-REQUEST CADENCE: 6.9% of all queries are a repeat of a (uri,kind) already asked in the same capture (881,666 distinct pairs out of 969,064 queries). Per capture dup rate: VIDEO.saz 5.7%, omg.saz 10.6%, all.saz 12.6%, spotify.saz 9.2%, pre-release.saz 67.4% (a tight polling loop on 225 MixState). Repeat-count histogram: 819,514 pairs asked once, 60,211 twice, 1,491 three times, tail up to 9.
  17. RE-REQUEST INTERVAL (n=59,569 repeats with timestamps): p10 = 0.0s, p25 = 0.8s, median = 6.5s, p75 = 10s, p90 = 14s, max 496s. 98.5% of repeats happen within 60s and 98.8% within 300s — i.e. repeats are near-duplicate churn inside one navigation burst, NOT TTL-driven refresh. A tiny in-memory dedupe/coalesce window of ~15s would eliminate almost all of it. Worst offenders: TRACK_V4 49,353 repeats (median gap 5.9s), 182 CONSUMPTION_EXPERIENCE_TRAIT 7,539 (median 11.3s), 12 EPISODE_V4 1,745 (median 0.1s — literally same-instant duplicates), 225 MixState 358 (median 0.0s).
  18. BURSTINESS: 94.2% of consecutive XM POSTs in a capture are less than 1s apart. Median inter-POST gap 0.02s, p75 0.07s, p90 0.4s. Burst chains (POSTs separated by <1s) reach 389 POSTs; p90 = 31 POSTs per burst. Pagination runs of consecutive same-kind-signature 300-entity POSTs reach 140 pages in a row (= 42,000 entities of one surface hydrated in one burst). The client fires these effectively in parallel, not serially throttled.
  19. REQUEST HEADER: BatchedEntityRequest.f1 = {f1 country, f2 catalogue, f3 task_id}. Across all 2,718 POSTs country/catalogue was constant ('NL','premium'). f3 task_id is 16 raw bytes and is present on every POST (exact distinctness not measured — the value is binary and was lossily decoded in this pass).
  20. HTTP shape: POST https://gew4-spclient.spotify.com/extended-metadata/v0/extended-metadata, Accept: application/protobuf, Content-Type: application/protobuf, Content-Encoding: gzip on the REQUEST body, Authorization: Bearer, Spotify-App-Version header. Response is content-encoding: zstd with cache-control: private, max-age=0 (per-entry TTL lives in the protobuf, not the HTTP header).

**findings:**
  1. The 300-entity ceiling is REFUTED as a hard limit and CONFIRMED as a client constant: Spotify-App-Version 129400583 never exceeds 300 entities/POST across 2,471 POSTs, but the older 129400583-predecessor 129300667 sent 500 routinely and 1,425 once — and the server answered all 1,425 with 200s. Wavee is free to batch above 300; 300 is just what current desktop does.
  2. The server returns exactly one EntityExtensionData per ExtensionQuery — 969,064 in, 969,064 out, in order. Wavee can index responses positionally instead of by (uri,kind) lookup.
  3. TOOLING BUG that silently corrupts response analysis: xmresp_lib.decode() uses zstd ZstdDecompressor().decompressobj().decompress(body), which stops at exactly 65,536 bytes. Every XM response body decoded to exactly 65536 and yielded truncated protobufs (57,111 items instead of 969,064 — a 94% data loss). The fix is zstd.ZstdDecompressor().stream_reader(io.BytesIO(body), read_across_frames=True).read(). Any earlier analysis pass using this library's decode() on large XM responses is invalid.
  4. SESSION-ID ENUMERATION TRAP: .saz files use variable-width session ids (raw/0001_c.txt in omg.saz, raw/001_c.txt in playback_remote.saz, raw/01_c.txt in final.saz). Slicing the first 4 characters silently drops entire captures — it made 9 of 13 captures look like they contained zero XM traffic.
  5. NEW KIND IDENTIFIED: 237 = type.googleapis.com/spotify.playlistmixing.extensions.mixthreebandwaveforms.ThreeBandWaveforms (52 queries, 3 POSTs, spotify:track, max 50 per POST, cache_ttl=3600). Not in the previously established identified list. It belongs to the same DJ/Mix lens family as 217/218/219/222/225 plus 142 LIST_TUNER_AUDIO_ANALYSIS.

Additional type_urls resolved this pass (request-side work but cheap to extract): 5 AUDIO_FILES=spotify.extendedmetadata.audiofiles.AudioFilesExtensionResponse, 85 ORIGINAL_VIDEO=spotify.bumblebee.originalvideo.v1.OriginalVideo, 98/99 AUDIO/VIDEO_ASSOCIATIONS=spotify.bumblebee.{audio,video}_associations.v1.*, 114=spotify.watchfeedextensions.api.v1.EntityExplorerEntrypointResponse, 136=spotify.playback_platform.transition.v1.TransitionMaps, 142=spotify.playlist.tuner.extension.ListTunerAudioAnalysis, 149=spotify.traits.v1.RootlistabilityTrait, 151=spotify.artistsectionprovider.v1.RecommendedPlaylists, 164=spotify.gatedentityrelations.v1.GatedEntityRelations, 170=spotify.autolensextension.v1.AutoLens, 205 LIST_METADATA_V2=spotify.list.v1.model.Attributes, 80 SHARE_TRAIT=spotify.traits.v1.ShareTrait.

Six kinds NEVER returned a payload in this entire corpus and are pure wasted bytes for this account/market (NL/premium): 30 EPISODE_ACCESS (0/1,644), 58 CONTENT_WARNING (0/1,196), 31 SHOW_ACCESS (0/516), 22 PODCAST_SUBSCRIPTIONS (0/126), 98 AUDIO_ASSOCIATIONS (1 of 11,869), plus 52/88 AUDIOBOOK_* (404) and 64 AUDIOBOOK_PRICE (400).   9. Transient server errors are real and must be retried: 699 x 502 and 488 x 504 appeared as PER-ENTRY status codes inside otherwise-HTTP-200 responses (concentrated in 182 CONSUMPTION_EXPERIENCE_TRAIT and 179 VISUAL_IDENTITY_TRAIT). The HTTP layer says 200; the entry says 502/504. Wavee must check EntityExtensionData.header.status_code per entry, not just the HTTP status.
  10. 6 TRACK_DESCRIPTOR is an etag anomaly: 95.9% of its queries carry an etag yet it returned 0 x 304 and 214 x 200 payloads. Sending an etag for kind 6 buys nothing. Same for 185 ON_PLATFORM_REPUTATION_TRAIT (25% etag, 0 x 304).
  11. cache_ttl values are per-kind and wildly different — 60s for 178 IDENTITY_TRAIT / 170 AUTO_LENS / 183 PUBLISHING_METADATA_TRAIT / 113 COMPANION_CONTENT, 600s for 12 EPISODE_V4 / 11 SHOW_V4 / 80 SHARE_TRAIT / 225 MixState, 3600s for most traits, 86400s for 249 ContentExperienceTrait / 98 / 99 / 5 AUDIO_FILES / 220, and 7,776,000s (90 days) for 4 PODCAST_SEGMENTS. offline_ttl is a flat 2,592,000s (30 days) for every single kind observed, without exception. 205 LIST_METADATA_V2 is the only kind that omits cache_ttl entirely.
  12. Practical batching recipe for Wavee: (1) one POST per surface carrying the whole kind-bundle for that surface rather than one POST per kind — the desktop client already does this and it collapses a 6-round-trip row hydration into 1; (2) page at 300 entities to match current desktop, or higher since the server tolerates 1425; (3) persist etags to disk keyed (uri,kind) — 87.5% of etag-bearing queries 304 and a 304 entry is ~20 bytes vs a full Track payload; (4) add a ~15s in-flight coalescing window keyed (uri,kind), which would remove ~99% of the 6.9% duplicate traffic the desktop client wastes.
