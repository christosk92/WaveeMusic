Wavee on large displays — current sizing vs. proposed

One mock surface — sidebar (wide tier) · a Comfortable-density track table · lyrics rail · player bar — drawn twice inside the same 3440 × 1392 px client area the author's 34″ ultrawide actually reports (\\.\DISPLAY1, OS scale 100 %, so 1 DIP = 1 px). Scroll each window sideways; they are the real width, not a thumbnail. Companion doc: large-display-scaling.md.

Every dimension below is authored as a DIP literal read off the code and multiplied by one CSS variable --z. That is not a prototype shortcut — it is exactly how the shipped app works: Win32Window._scale = _rawDpiScale × _zoom, and the layout tree never sees the scale at all. The only difference between the two windows is --z, plus one new lyrics measure cap.

A · Current — --z: 1 (zoom 100 %, the shipped default)

3440 DIP of window, 1600 DIP of design the complaint

Nothing here is a bug. Every constant is doing what it says: a 72-DIP bar, a 320-DIP pane, 14/20 row text, a 26-DIP lyric, and a content column capped at WaveeSize.PageMaxW = 1600 and centred. The app just has 2.07× the DIP width it was designed for, so all of it reads at half its intended proportion — and the page column is spending ~1500 DIP on empty gutters.

B · Proposed — --z: 1.5 (Auto zoom, plus a lyrics measure cap)

ZoomAutoPolicy.Suggest(3440, 1392) → 150 % recommended

min(3440 / 1600, 1392 / 900) = min(2.15, 1.55) = 1.55 → 150 %. The design box 1600 × 900 is not a new number: 1600 is WaveeSize.PageMaxW and 900 is DetailShell's own tall-hero gate. The min() is what stops the policy buying size by giving up structure — width alone would pick 200 %, whose 1720 × 696 DIP viewport demotes both the nav-pane wide tier (arms at 1800) and the TitleLarge hero rung (arms at 900 tall).

Rejected: automatic per-surface size tiers

A width-driven size ladder per surface rejected

"At > 2200 DIP make the bar 96, the rows 80, the type 18, the pane 400." It would look like window B — and cost the whole app to get there.

Blast radius: 799 const float declarations in src/apps/Wavee and ~27 pure layout test files that pin literals, each needing a tier axis. Re-opens a settled bug: a per-tier metric ramp once shipped three of six player-bar tiers with sub-WCAG hit targets — the reason PlayerBarLayout's metrics are deliberately flat today. Becomes a matrix: density × size-tier × width-tier. With zoom it stays one product, DIP(density, width-tier) × osDpi × zoom. And it structurally cannot work: MergedChromeLayout.FixedBudget is measured against native caption geometry (ChromeCaptionClusterW = 3 × CaptionButton.Width; ChromeMinDragStripW is pinned by TitleBar) — an app-level tier factor cannot move the OS caption buttons. Only the window scale moves both together, and it already does.

Also required — the one thing the recommendation itself breaks

Image decode budgets don't track the effective scale blocker

UseImage(src, decodePx) takes a caller-chosen budget and Wavee passes DIP-ish literals (Surfaces.cs:403, HomePage.cs:1622, ArtistPage.Hero.cs:327). Nothing multiplies them by Viewport.Scale. Landing Auto zoom at 150 % therefore decodes every cover at 1/1.5 the resolution it displays — the art tiles in window B above would be visibly soft in the real app, and the user would correctly blame the new feature. Fix in the same change: UseImage(src, ceil(dipEdge × UseContext(Viewport.Scale))), capped. Equalizer.cs:63 is the existing precedent for reading Viewport.Scale to size a device-pixel resource.
