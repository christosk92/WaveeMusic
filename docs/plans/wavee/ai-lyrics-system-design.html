Wavee On-Device Lyrics Engine

This document tells how Wavee changes line-synced lyrics into word-by-word lyrics on the user's PC. The engine runs two AI models on the NPU of a Copilot+ PC while the song plays. The audio and the lyric text do not leave the PC.

1Overview

The engine has one task. It finds the time at which the singer says each word of a lyric line.

The engine gets two inputs. The first input is the lyric text from a lyrics provider, usually Spotify. Spotify gives one start time for each line. The second input is the audio of the song. Wavee decodes this audio from the Spotify file.

The engine makes one output. The output is a lyrics document in which each word has a start time and an end time. The lyrics view then shows a word-by-word wipe.

The engine does the work in three phases:

  1. A separator model removes the instruments. Only the voice stays.
  2. An aligner model listens to the voice. It gives a probability for each letter every 20 ms.
  3. An alignment algorithm finds the one best path of the lyric letters through these probabilities.

The engine does not wait for the full song. It processes the audio in blocks, a little before the playhead. It gives each word its final time a short period before the user hears the word.

2Components and ownership

The code is in two repositories. The engine repository (FluentGpu) owns the Windows API calls. The app repository (Wavee) owns the AI pipeline, the user interface and the settings.

The ONNX Runtime binding stays in the app. ONNX Runtime is not a Windows service. Wavee downloads it at run time, and its API version is part of the model pack.

3Threads

The UI thread does not wait for the engine. It does not read files and it does not call the NPU. It only writes signals and sends commands.

One worker thread owns the NPU sessions. It runs one track job at a time. A download task runs separately. It sends progress to the UI thread not more than 10 times each second.

The driver reacts to these events:

  • Track change. The driver cancels the current job. It waits for the lyrics of the new track.
  • Lyrics arrive. The driver checks the results cache first. If the cache has the song, the driver shows it at once. If not, the driver starts a job.
  • Seek and pause. The driver does nothing. The job follows the playhead.
  • Battery saver on. The job stops, unless the user set "Keep running on battery saver".
  • Master switch off. The job stops and the models unload.
  • App exit. The download stops (the partial files stay), the job stops, and the worker ends within 2 s.

4The track pipeline

A track job has one loop. Each pass of the loop adds 8 s of letter probabilities. Then the Viterbi commits the words that the playhead will reach soon.

Memory

The job does not keep the full song in memory. The mix and the vocals are sliding windows. The parts that grow with the song are small: the 10 ms level envelope, the letter probabilities (32 values every 20 ms) and the Viterbi backpointers (2 bits for each state in each frame).

Frontier and playhead

The processing frontier moves about 10 times faster than playback (measured in the prototype). The engine commits a word only when the playhead is 8 s from it. At that time the Viterbi has already heard much more of the song. This makes the decision almost as good as an alignment of the full song.

Why the aligner has five graphs

The full wav2vec2 graph does not run on the NPU. We found two problems and we changed the graph for each problem:

  1. The NPU calculates a convolution with one input channel and stride 5 incorrectly (96% relative error). We replaced this first convolution with framing plus a matrix multiplication. The result is the same calculation, and the error is 0.1%.
  2. One large graph fails with QNN_COMMON_ERROR_MEM_ALLOC. We cut the model into five graphs. Each graph compiles and runs.

6Alignment

The alignment is CTC forced alignment. The lyric becomes a chain of tokens: one token for each letter and one separator between words. The chain has 2L + 1 states for L tokens, because a blank state is between each pair of tokens.

Rules that make the path correct

RuleValueWhy the engine uses it
Optional wordsskip cost 2 natsBacking vocals in parentheses are often quiet or absent in the separated voice. The path can go around them.
Line-time priorwindow = line start − 2 s to next line start + 2 s; 0.5 nats per second outsideChoruses with the same words can slide one bar late. The prior keeps each line near its Spotify time. It still corrects drift of about 2 s.
Just-in-time commitplayhead + 8 sAn early commit locks in errors on repeated lines. A late commit has more context.
Pruningstates before the committed tokenAfter a commit, the path cannot go back. This keeps committed words in order.
Backpointers2 bits per state per frameCodes: stay, from s−1, from s−2, from a skip edge. A 6-minute song uses about 30 MB at most.
Silence snapmax 400 ms backCTC marks a letter after its sound starts. A word that starts after silence moves back to the rise of the voice level.
Fillgap between neighbours; 300 to 400 ms per wordEvery word of the line text gets a time. Skipped optional words share the gap. A line with no timed word uses its line time.

From word times to the document

Each completed line becomes a Lyrics.Line with IsWordByWord = true. The syllable texts are the line text cut at each word start. Thus the syllable texts join back to the exact line text. The karaoke wipe measures against this text. Lines that are not complete keep the provider's line time.

7Lyrics store integration

The engine does not get lyrics itself. It waits until a lyrics surface asks the store for the lyrics of the current track. Thus the feature makes no extra requests to lyrics providers.

The engine sends each new version of the document through Lyrics.Store.Upgrade(Doc). The store accepts the document only if these conditions are true:

  1. The document has Generated = true and at least one line.
  2. The store already answered this track.
  3. Authority.IsRicher ranks the new document above the current document.

Each progressive document changes only the lines that got word times. The view changes the key of only those rows. The other rows do not mount again. Thus there is no flicker and no scroll jump.

The store writes nothing to the provider disk cache. A results cache in ai\lyrics\results\ keeps the final word times of each song, with a hash of the provider text. On the next play, the engine shows the cached result at once and does not use the NPU.

8Setup and download

The feature is off by default. The user turns it on in Settings › Appearance › Lyrics. Wavee then shows the download size. Nothing downloads before the user confirms.

An embedded manifest gives the URL, the size and the SHA-256 of each file. The manifest is compiled into the signed app. Thus a changed file on a server cannot install.

The model host is the Cloudflare R2 bucket wavee-ai-models. The objects are immutable. A file larger than 64 MiB is in parts (.part00, .part01, …). The host sends Cache-Control: public, max-age=31536000, immutable and supports HTTP Range requests.

Optimizing for the NPU

After the download, Wavee compiles each graph for this NPU. This happens one time. The card shows "Optimizing for your NPU" with progress for each graph. For English, the compile of 6 graphs takes about 60 s. If a driver update makes the compiled files old, Wavee compiles them again and tells the user why.

The C# engine is slower than the prototype. The cause is the CPU STFT and iSTFT around the separator: 45.2 s of the 54.8 s for a 177 s song. The NPU call itself is about 7.5 s for that song. A float SIMD FFT and the overlap of CPU work with the NPU call must make the separation not more than 1.5 times the NPU time.

12Status and limits

Limits

  • The engine runs only on a Qualcomm Hexagon NPU. It does not run on the CPU or the GPU.
  • The engine aligns English and Spanish lyrics.
  • The engine needs lyric text. It does not write lyrics from the audio.
  • Words in the first 1 to 2 s of a song can be late. The provider line timing shows until the word times arrive.
  • Podcasts and videos are not in scope.
