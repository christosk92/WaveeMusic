FluentGpu video and DRM playback engine

This document gives the technical design of the video engine in FluentGpu and its use in Wavee. It shows the threads, the frame paths, the composition tree, the window topology and the playback state. It also shows which parts of the design are complete and which parts are not complete.

1Scope and status

This document applies to the video subsystem of the FluentGpu engine and to the video code in the Wavee app. It does not apply to audio playback. It does not apply to PlayPlay, which is the audio DRM.

An audit found 164 defects in this subsystem. A team of agents now changes the code in four parallel lanes. Then a serial phase does the changes that cross more than one lane.

2System overview In progress

Wavee is one process. The engine has no separate video process. The pop-out window is a second engine host in the same process.

Media Foundation decodes the video. It writes the frames into its own swapchain. The engine does not copy the frames. DirectComposition (DComp) shows that swapchain below the UI. The UI cuts a transparent hole where the picture must show.

All Spotify video uses PlayReady. Thus the protected path is the usual path in Wavee. The clear path plays local files and module video.

Note

Before the fix, a detached child host wrote process-wide statics such as HostDispatch.Current. It set them to null when it closed. Now a child host does not write process-wide statics. The child also unmounts its component tree when it closes (F104, F112, F105).

The command queue of the clear engine is now safe for many writers (F203). The Wavee load worker does not write player state. It sends each write to the UI thread (F185).

4Clear video path In progress

The clear engine uses Media Foundation in windowless swapchain mode. The engine thread asks for the swapchain handle after the metadata loads. It publishes the handle in a snapshot. The UI thread reads the snapshot during a pump.

Rules

  • The engine does not mark a source as live when GetDuration returns NaN (F052).
  • The engine sets SetDefaultPlaybackRate and SetPlaybackRate together (F068).
  • The player clears the surface, natural size and position at each open (F122).
  • The player publishes the surface only on the first frame of the current source (F159).
  • Each open has a generation number. The player discards a session from an older generation (F141).

Planned All clear engines will share one D3D11 video device and one DXGI manager for each adapter (F067). The engine will dispose a faulted engine outside its lock (F062).

5Protected video path In progress

The native DLL FluentGpu.PlayReady.Native.dll holds one runtime for each process. The runtime has one protected media engine. Each source is a session with a custom media source and a feeder thread.

Open sequence after the fixes

  1. The session starts the feeder when it is created. The feeder does not wait for the CDM (F217).
  2. The runtime sets the start position before Play. It does not do a correction seek after CANPLAY (F222, partial).
  3. The runtime does not run the ITA preflight on the first attach (F038).
  4. The runtime always sets the default playback rate for each session (F033).
  5. The engine reports FORMATCHANGE as a size change only. It does not resize the swapchain again (F003, F199).
  6. The session hides its surface until the first frame of this attach. It hides the surface again on detach (F020, F267).

Segment store

  • A seek to a position that is not in the buffer flushes the store. The next sample is a keyframe (F034).
  • The store trims history only at a keyframe boundary (F046).
  • The byte cap and the time window use one consistent rule (F040).
  • A transient GET failure causes a retry with backoff. It does not end the track (F035).
  • WAITING and STALLED events set the state to buffering (F030).

Planned Attach replaces the source directly (F015). The runtime does not join the feeder on its own thread (F017). Native events go through a ring buffer, not through direct managed calls (F014, F192). The source sends a complete H.264 media type (F261, F028).

6Composition tree Implemented

Each window has one DComp target. The UI swapchain visual is on top. Video visuals are below it. The UI erases a hole with a DestOut operation. DWM shows the video through the hole.

Pixel rule R

The DComp rect and the erase rect use the same rounding rule. Round X, Y, Right and Bottom independently to the nearest device pixel. Use MidpointRounding.AwayFromZero. Thus the hole edge and the picture edge are on the same pixel (F073, F078, F088).

Other rules

  • The clip is in device space. It is not in the scaled content space (F088).
  • The black backing stops Mica and the desktop from showing through gaps (F086).
  • The engine hides a slot with a real remove. It does not use an empty clip (F081).
  • The erase honours the opacity and the corner radii of the element (F078).
  • On device loss, the engine disposes each presenter before it releases the DComp device (F075).

7Hole and picture sync In progress

The ghost on DRM video has one main cause. The hole is in the UI swapchain. The picture is a DComp visual. Before the fix, the two moved on two paths. They became visible in different DWM frames.

Implemented On the settle frame after a resize, the render thread drains the video placement before Present and DwmFlush (F101).

Planned The published render frame will carry an immutable array of video intents (X-02, F070, F183). The render thread will be the only reader. It will apply the intents for the parent and all children. Then it will do one Commit for each turn (X-01, F080, F208).

8Pop-out window topology In progress

The pop-out window is a detached child host. It runs on the UI thread of the main window. Its frames present on the same render thread. The fixes make sure that one window does not wait for the other window.

Rules

  • Implemented The child composites into its own swapchain. Before the fix, it wrote into the main back buffer and used the main latency credit. This caused 1000 ms timeouts (F090).
  • Implemented Each host has its own tile range. The tiles of one window cannot overwrite the tiles of the other window (F229).
  • Implemented Each swapchain holds its own latency credit. A credit clears only when a Present runs. A cloaked pop-out counts as parked (F107).
  • Implemented A park request interrupts the slot wait. The UI thread does not wait for a full render turn (F207).
  • Implemented Pacing, catch-up and the present ledger are per target. Only parent motion marks the parent tick as presented (F094, F097).
  • Implemented The child produces a frame only on the display tick. A secondary present does not block (F106; F085 partial, needs a measurement).
  • Planned The engine creates the child window hidden. It shows the window after the first present and the first video bind (F115, F110). Close waits only for the fences of that target (F117).
  • Planned A modal move or size of the pop-out does not stop the main frame loop (F093).

9Readiness and control plane In progress

Readiness tells the element when it can show the picture and remove the poster. Before the fix, readiness was one bit for the whole player. The bit did not reset on a switch. Thus the last frame of the previous video showed through the hole.

The element shows the picture only when all these conditions are true:

  1. The session is ready for the current source.
  2. This slot has a visual with a bound handle.
  3. The element is active.
  4. The viewport is not empty.
  5. The content is not audio only.

The element writes the visibility last. The session does not set the visibility itself (F074, F130, F076).

Implemented The element reads Buffering, ActiveCue and the area bounds only in the leaves that need them (F123, F124, F134). Geometry-only pumps skip the full session publish (F120).

Planned State, position, duration, errors and DRM phase will advance in the player, not in the element (X-04, F132). Then the playhead does not freeze when no element is mounted.

10Switch procedure Implemented

Wavee now keeps one MediaPlayer for the life of the process. A change between audio and video is a switch on the live engine. It is not a rebuild (F152, F190).

Rules

  • Each load has a cancellation token. A newer load cancels the older load before it opens (F155).
  • A late prepare from an old request cannot remove the prepare of a new request (F160).
  • A retryable fault on a live player causes an in-place retry. It does not cause a rebuild (F163).
  • The Switch path sees open failures (F157).
  • The main presenter stays mounted under immersive lyrics and during a pop-out hand-off (F168, F180).
  • The warm keeper warms the runtime only when a video row plays and the user used video in this session (F165, F218, F225).
  • A prepared session expires from its last use, not from its creation (F007).

11Adaptive bitrate Implemented

The ABR controller selects a representation (a rung) for the protected stream. Before the fix, a cap change selected rung 0. Each switch also deleted the buffer.

  • The policy cap and the viewport cap are separate values. MaxHeight stays as a compatible property (F149).
  • The viewport cap applies only after the geometry settles (F140, F175).
  • The controller resets for each new source (F149).
  • A small slice has less weight than a full segment (F150).

13Frame production policy Planned

Steady UI work also loads the GPU that the video uses. On the owner's Adreno X1-85 at 120 Hz, the lyrics stepper alone causes about 115 presents per second.

  • The engine will apply a central cadence cap. On a weak GPU, loops run at 30 Hz or less (F245).
  • An inactive or covered window will throttle all autonomous wakes (F241, F118).
  • Marquees will move in whole pixels at about 30 Hz (F239).
  • The governor threshold will be a fraction of the display period (F250).
  • The lyrics stepper, the equalizer and the seek rail will run only when they are visible (F237, F240, F182).

15Change process In progress

For each package, do these steps:

  1. A Sonnet 5.5 agent reads the finding specifications and changes the code.
  2. An Opus 5.5 agent reviews the change. It also checks the code as a compiler would.
  3. If the reviewer finds a problem, the Sonnet agent corrects it. This can occur two times.
  4. The reviewer stages the approved change. Nothing is committed and nothing is pushed.
Note

The work is in separate worktrees under C:\wavee\vfix. The owner's checkouts and the running Wavee are not changed.
